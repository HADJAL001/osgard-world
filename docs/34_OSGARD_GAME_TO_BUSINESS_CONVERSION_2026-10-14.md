## Аудит перед изменением

В репозитории уже есть React/Vite/TypeScript портал, 11 игр, страницы деталей игр, контекстные рекомендации, форма разработки с безопасным fallback, отдельная Partner Studio, Node/PostgreSQL Commerce API, UTM-параметры, согласие на необязательную аналитику и коммерческий release gate. Новый отдельный портал, ещё один analytics SDK или фиктивный рекламный блок только продублировали бы имеющиеся системы.

Выявленный пробел: страница каждой игры помогала перейти к следующей игре, но не предлагала отдельный, спокойный путь от интереса к игре к двум коммерческим действиям OSGARD — заказу собственной игры и запросу спонсорской интеграции. В Partner Studio UTM-контекст попадал в описание заявки, но не передавался отдельно в структурированные поля attribution API, поэтому игра-источник могла оставаться unknown в сводках.

## Что реализовано

1. После блока похожих игр добавлен адаптивный CTA-блок OSGARD / FROM PLAY TO PRODUCT.
2. Кнопка «Обсудить создание игры» открывает существующую форму /development#project-intake с utm_source=osgard_games, utm_medium=cross_promo, utm_campaign=game_detail_intake, utm_content=<game-id> и game_id=<game-id>.
3. Кнопка «Обсудить спонсорство» открывает существующую Partner Studio с предвыбранным форматом «Спонсорское событие или уровень» и кампанией game_detail_sponsorship.
4. Ссылки строятся через URLSearchParams, не переносят пользовательский текст, токены или referrer URL и не создают автоматический переход в сторонний сервис.
5. При явном согласии переходы отправляют только минимальное событие cross_promo_clicked через same-origin Commerce API. Не передаются cookies, auth-токены, контакты, query string или referrer. Без согласия функция немедленно прекращает работу; ошибка отправки не блокирует навигацию.
6. commerce-client.js извлекает game/source/campaign по allow-list, нормализует slug и передаёт их как структурированный объект attribution вместе с заявкой. Сервер самостоятельно повторно валидирует game ID/source/campaign.
7. Сохранены существующие формы, проверка согласия на обработку, серверный honeypot, rate limit, сообщения об ошибке и ручная отправка через WhatsApp. Если API пуст или недоступен, интерфейс не утверждает, что заявка сохранена.
8. Добавлен npm run qa:game-business-bridge и подключён к PR quality, growth и production deploy workflows.

## Приватность и честность

- Сам клик не отправляет контактные данные и не означает, что человек стал лидом.
- Необязательная аналитика по-прежнему выключена по умолчанию; анонимное событие cross_promo_clicked отправляется только после opt-in. Для хранения результата нужны доступные Commerce API и база.
- Атрибуция кампании записывается в заявку только после нажатия кнопки отправки и явного согласия на обработку заявки.
- Лид не является подтверждённым заказом. Покупки, оплаченные продажи, рекламные показы и доход не создаются этой функцией.
- Доступность production API/базы и фактический деплой остаются отдельными проверками; пустой API config нельзя трактовать как успешное сохранение.

### Анонимная согласуемая аналитика конверсий

Для коммерческих CTA используется src/core/gameConversionAnalytics.mjs вместо журнала player event queue, так как последний в штатном режиме синхронизируется при наличии авторизованного player API. Новая функция отправляет краткий event с tab-scoped session id на /commerce-api/v1/events только после явного аналитического согласия. Запрос использует credentials=omit, не добавляет auth-токен и содержит только gameId из allow-list, один из двух destination labels и pathname без query string. Отправка best-effort: ошибки не блокируют переход и не объявляются успешной записью.
