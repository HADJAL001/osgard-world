# OSGARD WORLD — Commercial Readiness Gate
Дата: 14 октября 2026 года
Репозиторий: HADJAL001/osgard-world

## Зачем это изменение

В репозитории уже существует React 19 / Vite 6 / TypeScript-экосистема, одиннадцать игровых точек входа с разными рантаймами, согласуемая аналитика, каталог партнёров, кампании и Commerce API на Node.js + PostgreSQL + Stripe. Перенос всех игр на один движок создаст лишний риск и не нужен: NULL//SHIFT использует Godot Web export, REMIX — Unity WebGL, остальные игры работают как веб/React-клиенты.

Следующий риск находится не в количестве экранов, а в возможности ошибочно принять «настроено» за «готово к коммерческому запуску». Добавлен защищённый read-only endpoint и объединённая панель релизной готовности.

## Что изменено

- Новый GET /v1/admin/readiness защищён тем же bearer-токеном, что и другие административные маршруты.
- Endpoint запускает действующую серверную проверку цен через Stripe (где это возможно) и отдаёт только редактированные статусы; секреты, Price ID, URL базы и токены не возвращаются.
- В Commerce Admin появляется список готовности базы, заявок, согласуемой аналитики, разовых checkout-цен, статуса Stripe/webhook, Premium, спонсорского инвентаря, рекламной сети, внешних доменов и production-release.
- Цветовые статусы различают готовое, test-only, заблокированное, требующее ручной проверки и неинтегрированное.
- Состояния test и live разделены: конфигурация тестовой цены не является live-выручкой; live-конфигурация требует ручной проверки до запуска кампаний.
- Продажа OSGARD PREMIUM дополнительно защищена серверной константой PREMIUM_ENTITLEMENTS_IMPLEMENTED = false. Одной переменной окружения больше недостаточно: сначала нужны реальные права подписчиков, выдача/отзыв доступа, отмена, возвраты и опубликованные условия.
- Наличие конструктора спонсорских кампаний явно не называется подключённой рекламной сетью. В коде нет рекламного SDK; система не заявляет рекламные показы или выплаты.
- Добавлены unit-тесты read-only модели готовности и статические интеграционные проверки.

## Статусы

- ready: компонент доступен согласно данным серверной среды.
- test_only: компонент проверен, но только на тестовом Stripe-режиме.
- blocked: отсутствует обязательная предпосылка или есть жёсткая продуктовая защита.
- armed: live-переменная явно включена; это предупреждение, не рекомендация запускать публичную рекламу.
- review_required: нужен контрольный тест, подтверждение домена/условий или ручной релизный gate.
- not_integrated: в репозитории нет интеграции соответствующего внешнего провайдера.

## Ограничения и безопасность

- Endpoint только читает состояние и не меняет env, цены, кампании, платежный режим или продуктовый доступ.
- Отчёт не доказывает, что front-end live deployment состоялся. Это подтверждает только успешная выкладка и post-deploy route matrix.
- «Готовая аналитика» относится к соглашаемой серверной телеметрии и не равна всем посещениям или рекламным impressions.
- Статус внешних доменов не вычисляется живым HTTP-запросом из API. Перед платной кампанией нужно вручную проверить контроль домена, HTTPS, продукт, условия, контакты, редиректы и безопасный платёжный путь.
- Платёжные цены проверяются при запросе readiness. Нельзя вводить платёжные секреты в браузер; конфигурация остаётся в серверных переменных.
- Изменения не включают live checkout, рекламную сеть, подписки или автоматический production deploy.

## Проверка

CI для Commerce запускает:
1. npm test в services/osgard-commerce-api, включая readiness.test.mjs.
2. npm run check (синтаксис API и readiness-модуля).
3. node scripts/commerce-rollout-smoke.mjs (статические контракты API/admin/config).

После merge/release дополнительно нужны: успешный GitHub Actions, тестовый Checkout и webhook, проверка no-token = 401, готовность базы, тест отмены и возврата, post-deploy route matrix и ручной desktop/mobile QA. В текущем окружении production-сайт и внешние домены не были подтверждены живым запросом; это изменение само по себе не публикует сайт.
