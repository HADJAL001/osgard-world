# OSGARD PLAY — Campaign Manager: 30 конкретных улучшений
Дата: 14 октября 2026 г.
Ветка: `feat/osgard-sponsor-campaign-manager-20261014`
Основа: актуальный на начало переноса master `b529dda9c66a6bae9e6291c8396c1e2bdb2f1752` репозитория `HADJAL001/osgard-world`; интеграционная ветка пересоздана поверх этого состояния, чтобы сохранить параллельные изменения.

## Аудит до изменений
В репозитории уже есть Vite/React/TypeScript, 11 независимых игровых точек входа, каталог Games, Player Lab, постигровые рекомендации, локальные предпочтения, consent-gated аналитика и Commerce API с PostgreSQL/Stripe-подготовкой. Partner Studio уже описывает форматы, но все placement были неактивны; редактор инвентаря работал только локально и не сохранял кампании в серверную базу. Production checkout, Premium и Commerce API публично не считаются активированными: `commerce-config.json` пустой, платежные флаги должны оставаться выключенными до настройки инфраструктуры.

## Реализованные изменения
1. Создан отдельный серверный реестр рекламных кампаний, не заменяющий существующий каталог.
2. PostgreSQL схема `commerce_campaigns` создаётся существующим миграционным boot-путём.
3. Создание кампании защищено существующим `requireAdmin` и Bearer-токеном.
4. Чтение и обновление кампаний также требуют авторизации.
5. Административные ответы помечены `no-store, private`.
6. Публичный API возвращает только прошедший allow-list проекцию полей.
7. Текстовые поля ограничены длиной и очищаются от управляющих символов.
8. Произвольный HTML не принимается как поле интерфейса и не рендерится.
9. URL разрешены только HTTPS, без учётных данных, query-параметров и fragment.
10. Маркировка `Реклама`, `Партнёрский материал` или `Спонсорский материал` обязательна.
11. Статус проверяется по allow-list: draft/scheduled/active/paused.
12. Размещение проверяется по allow-list.
13. Активная кампания обязана иметь окно публикации, включающее текущий момент.
14. Запланированная кампания обязана начинаться в будущем.
15. Даты проходят ISO-нормализацию и проверку порядка.
16. Частотный лимит — целое значение 1–20 с серверной проверкой.
17. В публичный слот допускаются только кампании `catalog_feature`.
18. Неподключённые after-session и in-game форматы нельзя сделать active.
19. Активная витрина ограничена тремя карточками.
20. Advisory lock сериализует публикацию и защищает от конкурентного переполнения трёх слотов.
21. API скрыт в fail-closed состоянии, пока PostgreSQL не готов.
22. Админка имеет отдельный `noindex,nofollow,noarchive` route.
23. Административный токен хранится только в памяти вкладки, не пишется в localStorage.
24. API base берётся из явного config и валидируется как безопасный HTTPS endpoint.
25. Интерфейс адаптирован под desktop/tablet/mobile и системное reduced-motion preference.
26. Клавиатурная навигация, видимые focus states, статусные сообщения и подписи полей добавлены.
27. Есть создание, редактирование и пауза кампании; удаление не используется вместо аудита статусов.
28. В каталоге появился лениво загружаемый спонсорский блок, скрытый при пустом API или ошибке.
29. Частота экспозиции ограничивается локально на устройстве/24 часа; когда браузерное хранилище недоступно, рекламный слот скрывается. Это не межустройственный глобальный cap.
30. Реальные видимые показы и клики передаются только через существующую consent-gated очередь аналитики; административный список сводит подтверждённые события за 30 дней. UTM переходы сами по себе не интерпретируются как продажи.

## Коммерческие и технические границы
- Это менеджер спонсорского инвентаря, а не интеграция сторонней ad network. Rewarded-video/ad callbacks не добавлены.
- Активный слот каталога требует развёрнутого Commerce API, PostgreSQL и заполненного `public/games/commerce-config.json`. При пустой конфигурации public block остаётся скрытым.
- Оплаченные объявления не должны появляться до договора, проверки рекламодателя/ссылки и юридического согласования.
- Публичный API никогда не отдаёт админский токен или внутренние поля записи.
- Переходы помечаются UTM; фактическая конверсия у получателя подтвердится только при независимой аналитике на сайте назначения.
- Аналитика показа/клика требует явного согласия. Без него события не отправляются.
- Existing Stripe checkout/Premium flags are unchanged; live payments remain gated.

## Ввод в эксплуатацию
1. Открыть PR и дождаться зелёных CI checks.
2. Развернуть обновлённый Commerce API и дождаться `/readyz` (для campaign endpoints необходим PostgreSQL; Stripe не нужен для самих кампаний, общий /readyz в текущем сервисе при этом дополнительно зависит от Stripe).
3. Добавить HTTPS API URL в `public/games/commerce-config.json` после проверки same-origin proxy/CORS.
4. Открыть `/games/admin/campaigns/`, использовать действующий `ADMIN_API_TOKEN`, создать сначала draft и проверить внешний URL.
5. Активировать только после подтверждения рекламодателя, прав использования материалов, disclosure и периода размещения.
6. Проконтролировать consented impressions/clicks в Campaign Manager. До включения сторонней рекламной сети подписать договор и провести отдельную интеграцию/QA.
