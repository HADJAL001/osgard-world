# OSGARD WORLD — аудит игровой платформы и выпуск

Дата аудита: 13 октября 2026 года  
Репозиторий: **HADJAL001/osgard-world**  
Рабочая ветка изменений: **codex/osgard-game-platform-v1**

## Краткий итог

Существующий портал не нужно переписывать с нуля. Это приложение на React 19, TypeScript и Vite; в зависимостях также используется Three.js. Уже существуют основная страница портала, раздел Entertainment, общий манифест пяти игр, очередь событий и production-проверка маршрутов. Игры используют разные способы запуска — поэтому весь каталог нельзя бездумно переносить на один движок.

Эта работа добавляет отдельную игровую витрину и не удаляет старый маршрут /entertainment. Публикация в master и на production-сервер не выполнялась.

### Пять существующих игр

| ID | Текущая точка запуска по манифесту | Технологическая особенность |
| --- | --- | --- |
| time | /games/time | React-маршрут портала с отдельным игровым интерфейсом |
| swarm | /games/swarm/index.html | Отдельный браузерный клиент; для сетевого режима важна доступность существующего API |
| null-shift | /games/null-shift-godot/index.html | В манифесте и production route matrix предусмотрена отдельная веб-сборка Godot; репозиторий также содержит браузерный WebGL-клиент в /games/null-shift/ |
| inherit | /games/inherit/index.html | Самостоятельная браузерная игра |
| remix | /games/remix/index.html | Unity WebGL; пакет включает крупные .wasm.gz и .data.gz-ресурсы |

**Риск, который необходимо проверить на сервере:** текущий репозиторий показывает браузерные файлы NULL//SHIFT в /games/null-shift/, в то время как production route matrix ожидает отдельный Godot-экспорт по /games/null-shift-godot/. Эту разницу нельзя «исправлять» переписыванием ссылки без проверки готового production-архива и фактического сервера.

## Реализовано в этой ветке

Новая игровая платформа доступна по задуманным маршрутам:

- /games — каталог с поиском, фильтрами по жанрам, избранным и недавними играми;
- /games/info/:id — страница игры с описанием, типом запуска, проверкой обязательных URL, сведениями об управлении и устройствах;
- /games/play/:id — встроенное игровое окно, полноэкранный режим, выход к прямому URL игры и статус загрузки.

Другие изменения:

- Главные ссылки «Развлечения / все игры» ведут к новой витрине; старый /entertainment сохранён как резервный маршрут.
- Проверка точки запуска использует HEAD, тайм-аут и тип ответа. Она показывает только доступность URL/файлов — **не** обещает, что 3D-движок успешно стартовал или что игра работает на реальном телефоне.
- Избранное и список недавних игр сохраняются в локальном браузере, но не синхронизируются между устройствами.
- Поиск работает с клавиатурным сочетанием Ctrl/⌘ + K; интерфейс уважает prefers-reduced-motion, использует заметные состояния фокуса и адаптируется к мобильным экранам.
- Встроенный плеер записывает уже поддерживаемые события game_opened, game_session_started, game_session_completed и share_created. Продолжительность сессии считает только время, когда вкладка видима, отдельно сохраняя полное прошедшее время.
- Добавлен scripts/games-platform-smoke.mjs; CI запускает npm run qa:games-platform. Production route matrix расширена маршрутами новой витрины.
- CTA на разработку ведёт в существующий /development; email и WhatsApp добавлены в футер каталога.

## Что не заявлено как готовое

1. Live-сайт и его внешние продуктовые домены не удалось проверить из текущей среды: сетевой запрос завершался ошибкой DNS/Cache miss. Изменения на публичный сервер не отправлялись.
2. Pull request — это подготовка изменения в репозитории, но не его публикация. Требуются результаты GitHub Actions и production route matrix после разрешённого развёртывания.
3. Рекламная сеть не подключена: в репозитории в рамках этой работы не обнаружены предоставленные рекламные ключи или подтверждение одобрения аккаунта.
4. Провайдер платежей, серверная проверка покупок, права на товары/подписку и возвраты не реализованы этой веткой.
5. Административный интерфейс управления рекламой/каталогом и управление согласием для необязательной рекламы ещё требуют отдельной реализации. Не добавлять SDK до выбора провайдера, проверки его требований и юридической модели.
6. Эта витрина не доказывает runtime-совместимость игры. Отдельно нужны тесты игрового движка и физические устройства.

## Финансовая модель — только иллюстративные допущения

Это не результат рыночного исследования и не прогноз гарантированного дохода. Числа нужны, чтобы было видно, какие показатели необходимо измерять и как они влияют на экономику.

Формулы:

- Начавшие игру = визиты × доля посетителей, запустивших игру.
- Рекламные показы с заполнением = визиты × доля запусков × сессии на игрока × рекламные места за сессию × fill rate.
- Доход от рекламы = заполненные показы ÷ 1 000 × eCPM.
- Плательщики = начавшие игру × доля плательщиков.
- Поступления от покупок = плательщики × среднее поступление на плательщика.
- Ожидаемый вклад лидогенерации = визиты × конверсия в заявку × конверсия заявки в заказ × вклад одного выполненного заказа.
- Остаток сценария = реклама + покупки + ожидаемый вклад лидогенерации − условные операционные расходы.

| Показатель за месяц | Консервативный | Базовый | Оптимистичный |
| --- | ---: | ---: | ---: |
| Визиты | 5 000 | 30 000 | 150 000 |
| Доля, запустившая игру | 25% | 35% | 45% |
| Начавшие игру | 1 250 | 10 500 | 67 500 |
| Сессий на начавшего игрока | 3 | 4 | 5 |
| Рекламных мест на сессию | 2 | 2,5 | 3 |
| Fill rate (допущение) | 35% | 55% | 70% |
| eCPM (условные USD) | $1,50 | $3,00 | $5,00 |
| Расчётные рекламные поступления | $3,94 | $173,25 | $3 543,75 |
| Доля плательщиков от начавших | 0,1% | 0,35% | 0,75% |
| Среднее поступление на плательщика | $4 | $5 | $7 |
| Расчётные поступления от покупок | $5,00 | $183,75 | $3 543,75 |
| Конверсия визита в заявку на разработку | 0,05% | 0,15% | 0,30% |
| Конверсия заявки в выполненный заказ | 10% | 15% | 20% |
| Условный вклад одного выполненного заказа | $300 | $600 | $1 000 |
| Ожидаемый вклад лидогенерации (не обязательно фактическая выручка этого месяца) | $75 | $4 050 | $90 000 |
| Условные ежемесячные расходы | $150 | $500 | $2 500 |
| Расчётный остаток после этих расходов | −$66,06 | $3 907 | $94 587,50 |

Вклад лидогенерации доминирует в двух последних сценариях. Это лишь арифметика по очень чувствительным допущениям, а не основание для бюджета: фактические заявки, закрытия, маржа и сроки поступления денег должны измеряться отдельно. До запуска нужно вычесть платежные комиссии, налоги, возвраты, стоимость разработки/поддержки и возможную модерацию.

### Что измерить первым

1. Фактические визиты и старты игр с одного источника аналитики.
2. Длительность видимой сессии, повторный запуск и переход из игры к следующей игре.
3. Заявки /development с источником перехода и итогом квалификации; не передавать личные контакты в рекламные параметры.
4. После получения одобрения рекламной сети — реальные заполненные показы и отчёт сети, а не простое количество загруженных рекламных блоков.
5. Покупки — только после выбора платёжного провайдера, серверного подтверждения транзакции и тестирования возвратов.

## Запуск и выпуск

### Локальная проверка

Команды для запуска из корня репозитория:

- npm ci
- npm run check
- npm run qa:games-platform
- npm run build
- npm run qa:release
- npm run qa:production-routes

qa:production-routes по умолчанию проверяет https://osgard.world. Если DNS или доступ к production недоступны, этот этап нужно повторить из среды, имеющей доступ к домену. Успешная локальная сборка не равна доказательству, что public сайт выдаёт новый bundle.

### Безопасная публикация

- Проверить GitHub Actions для PR и сохранить лог проверки.
- Убедиться, что файлы Godot-экспорта, API SWARM и Unity/WebGL REMIX действительно присутствуют на целевой стороне, с корректными MIME-типами.
- Запустить desktop/mobile route matrix после выкладки в staging.
- Использовать существующий staging/rollback процесс из DEPLOYMENT.md; не очищать live-папку перед проверкой нового архива.
- Production workflow намеренно ручной и требует секреты OSGARD_DEPLOY_HOST, OSGARD_DEPLOY_USER, OSGARD_DEPLOY_KEY. Не заменять их личным root-ключом и не записывать значения в репозиторий.

### Следующие коммерческие шаги

1. Подтвердить работоспособность каждой точки запуска на production.
2. Собирать базовые показатели стартов, видимых сессий, возврата к игре и переходов в /development.
3. Увидеть реальную конверсию в заявки, прежде чем вкладываться в дорогостоящую рекламную инфраструктуру.
4. После выбора рекламной сети — сделать маркированные места вне критического игрового поля, проверить политику согласия и только затем включать SDK.
5. Подписку и покупки начинать после проверки спроса и безопасного серверного учёта прав доступа.
