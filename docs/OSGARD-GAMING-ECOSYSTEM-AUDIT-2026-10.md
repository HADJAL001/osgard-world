## Краткий вывод

В репозитории уже есть полноценная основа игровой платформы; начинать её заново или создавать параллельный портал не нужно. Основной фронтенд — React 19 + TypeScript + Vite 6. Игры каталога в основном отдаются как самостоятельные статические веб-проекты из public/games/; отдельные проекты могут зависеть от игрового API, а NULL//SHIFT описан в каталоге как Godot-сборка с браузерной WebGL-альтернативой. В отдельном сервисе services/osgard-commerce-api используются Express 5, PostgreSQL и Stripe SDK.

## Что обнаружено в исходниках

- **Каталог:** public/games/index.html и public/games/game-catalog-fallback.json; в контракте зарегистрировано 12 игр. Есть карточки, поиск/фильтры, страницы отдельных игр, метаданные для поисковиков и социального предпросмотра, PWA-обвязка.
- **Изменение каталога:** public/games/admin/catalog/ и API /v1/admin/game-catalog. В интерфейсе токен оператора хранится в памяти вкладки; запись проверяется сервером по allow-list игровых маршрутов.
- **Коммерческая инфраструктура:** отдельные маршруты для каталога, кампаний, заявок и checkout в commerce API. Stripe и PostgreSQL включаются конфигурацией окружения; наличие кода не доказывает, что production-ключи, база и вебхуки настроены.
- **Аналитика:** события каталога и игр имеют ограниченный список допустимых типов. В public/games/consented-analytics.js отправка необязательной игровой аналитики требует явного согласия; React-приложение также содержит AnalyticsConsentControl.
- **Самореклама и партнёры:** есть межигровые предложения с настройками частоты, public/games/sponsored-campaigns.js с маркировкой рекламы и ограничением частоты, страница /games/partners/ для заказных/спонсорских интеграций.
- **Десять направлений экосистемы:** в scripts/external-project-healthcheck.mjs уже заведены десять заданных доменов. В src/Development.tsx есть портфолио с описаниями и переходами; в src/PlaySelectLoop.tsx — настраиваемая межсессионная подборка.
- **QA:** в package.json есть build/check команды и существующие smoke-тесты каталога, игр, партнёров, аналитики, кампаний, экономики и выпуска.

## Обнаруженный дефект и изменения в этой ветке

1. **Потеря коммерческой атрибуции HEIST//ECHO.** Канонический каталог, TypeScript-тип игровых ID и серверный каталог уже включали heist-echo, но allow-list ATTRIBUTION_GAME_IDS в public/games/commerce-client.js отставал на один ID. Заявки с game_id=heist-echo могли потерять исходную игру и получить unknown. Исправлено добавлением ID.
2. **Атрибуция переходов из портфолио экосистемы.** Карточки в src/Development.tsx теперь записывают событие cross_promo_clicked через существующий consent-gated event queue. UTM-параметры добавляются только при сохранённом согласии; без согласия ссылка остаётся обычной, события не сохраняются.
3. **Регрессионный контракт.** Добавлен scripts/game-attribution-contract-smoke.mjs, который сверяет игровые ID в fallback-каталоге, фронтенд-типе, серверном каталоге и клиентском allow-list атрибуции, а также проверяет, что кросс-промо не включается до согласия. Проверка добавлена в цепочку npm run qa:games-portal.

## Что не удалось подтвердить из этой среды

- Прямое открытие https://osgard.world/games/ и сетевые запросы к указанным внешним доменам из текущего runtime блокируются/не проходят DNS-разрешение. Это **не является доказательством, что сайты недоступны для пользователей**; реальную доступность следует проверить повторно из CI или обычной сети.
- Невозможно сделать вывод, что production-каталог, commerce API, PostgreSQL и платежи реально работают, пока не проверены опубликованные маршруты и переменные окружения. Секреты не нужны в клиентском коде и не включены в эту ветку.
- Статические проверки исходников не заменяют браузерный smoke-тест опубликованной версии и тестовый checkout через Stripe test mode.

## Команды следующей проверки

    npm ci
    npm run check
    npm run build
    npm run qa:games-portal
    npm run qa:games-model
    npm run audit:external-projects
    npm run qa:external-project-healthcheck

Затем из сетево-доступной среды проверить production route matrix и health/readiness commerce API. Платёжный тест проводить только с тестовым Stripe-аккаунтом и настроенным подписанным webhook. До этого нельзя объявлять монетизацию активной или оценивать фактический доход.

## Приоритет внедрения

1. Пройти CI и исправить найденные регрессии.
2. Выполнить фактическую проверку десяти внешних доменов и публичных игровых маршрутов с сетевого runner.
3. Сверить production env для API/DB/Stripe и провести тестовый заказ.
4. Сопоставить реальные consented-события с заявками/платежами; только после сбора данных пересматривать рекламные места, тарифы и прогноз дохода.
5. Не начинать подписку/платёжную миграцию или перевод всех игр на один движок без подтверждённой продуктовой необходимости.
