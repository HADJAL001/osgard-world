# OSGARD PLAY — 30 improvements: Player Feedback & Quality Loop

Дата: 14 октября 2026 года.  
Базовая ветка: master; рабочая ветка: feat/osgard-game-feedback-loop-30-20261014.  
Задача: замкнуть цикл «игрок сообщает → команда воспроизводит → статус исправления проверяется», не создавая фиктивную статистику.

## Аудит перед реализацией

В репозитории уже есть React 19/Vite/TypeScript, 11 игровых маршрутов, каталог, PWA, Player Lab, согласуемая аналитика, панели операций и рекламных кампаний, а также подготовленный Commerce API с PostgreSQL. У отдельных игр собственные технологии (включая Unity WebGL и Godot Web export), поэтому переносить их все на один движок было бы необоснованно. Публичный commerce-config.json оставлен с пустым apiBaseUrl; этот релиз не включает оплату и не активирует внешнюю рекламу.

## 30 реализованных улучшений

### Обращение игрока
1. Создана отдельная премиальная страница обратной связи OSGARD PLAY.
2. Игрок выбирает одну из 11 игр или каталог целиком.
3. Добавлены категории ошибки, управление, механика, производительность, доступность, визуал, монетизация и другое.
4. Уровень важности разделён на небольшую, серьёзную проблему и блокирующую ошибку.
5. Заголовок и описание имеют явные минимальные и максимальные длины.
6. Отдельные поля ожидаемого и фактического результата упрощают диагностику.
7. Шаги воспроизведения доступны без обязательного заполнения.
8. Email для обратного ответа необязателен и валидируется.
9. Счётчик символов обновляется по вводу.
10. Есть доступные статусы формы через ARIA live region.
11. Экспорт JSON позволяет не потерять отчёт при ненастроенном сервере.
12. Копирование текста — альтернативный путь ручной передачи.
13. При отсутствии подтверждения сервером UI не объявляет отчёт сохранённым.
14. Учитываются системные размеры окна, округлённые до 50 px, без полного User-Agent.
15. Семейство браузера и класс устройства ограничены фиксированными значениями.

### Надёжность и безопасность
16. API принимает только allow-list известных игровых ID и полей.
17. UUID отправки обеспечивает идемпотентность повторного запроса.
18. Публичный endpoint ограничен пятью запросами за 15 минут на лимитер.
19. Honeypot отсеивает простейших ботов без сохранения отчёта.
20. Чтение очереди защищено requireAdmin и Bearer-токеном.
21. Изменение статуса также требует административную авторизацию.
22. В админ-панели токен находится только в памяти страницы, не записывается в Web Storage.
23. Админ-ответы получают no-store/private заголовки.
24. Тексты отчёта отображаются через textContent, а не вставляются в HTML.
25. Контакты хранятся только в отдельном поле отчёта и доступны лишь защищённой очереди.
26. Установлен отдельный настраиваемый срок хранения заявок; его фактическое значение зависит от окружения API.
27. Отчёт не входит в очередь игровой аналитики и не содержит поля IP или полного User-Agent.
28. Конфигурация API не может перенаправить контактные данные на произвольный домен; разрешён текущий origin и поддомены osgard.world.
29. Серверные/DB ошибки и HTTP 429 показывают понятный путь восстановления без фиктивного успеха.
30. Добавлены unit-тесты, статический smoke-контракт и маршруты страницы в production route matrix.

## Что пока не активировано

Публичная форма и административная страница готовы в коде. Хранение заработает только после деплоя обновлённого Commerce API с PostgreSQL и настройки apiBaseUrl на same-origin /commerce-api (или доверенный поддомен OSGARD). До этого форма явно предлагает экспорт JSON/копирование и не утверждает, что отправила заявку. Это ветка разработки и PR, не подтверждение обновления production. Требуется CI и реальный тест на HTTPS.
