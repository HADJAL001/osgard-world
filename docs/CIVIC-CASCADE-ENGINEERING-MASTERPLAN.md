# CIVIC CASCADE — инженерный мастер-план

**Статус документа:** инженерная стратегия и релизная политика.  
**Текущая базовая версия:** 3.2.0 — девять проверок чувствительности в трёх семействах стрессов плюс Pareto-портфель и воспроизводимое досье.  
**Продуктовая цель:** превратить CIVIC CASCADE из набора кризисных кнопок в объяснимую, проверяемую симуляцию принятия решений — без ложных обещаний об ИИ, физических моделях и живой телеметрии.

## 1. Архитектурный принцип

Состояние города — единственный источник истины. Реальные игровые действия, превью очереди, прогноз и автономный планировщик должны использовать одну и ту же модель эффектов. Планировщик никогда не изменяет рабочее состояние: он получает копию состояния, проверяет допустимость последовательности, моделирует последствия на горизонтах 30/60/90 игровых секунд и сравнивает результат с базовой траекторией без новых приказов.

Новая версия добавляет ограниченный deterministic beam search: глубина не больше четырёх команд, ширина фронта шесть кандидатов, ремонт рассматривается для трёх наиболее слабых узлов и выбранного оператором узла. Целевая функция выбирается явно: баланс города, снижение общего риска, защита инфраструктуры или экономия ресурсов. Планировщик показывает до трёх допустимых альтернатив; найденный план никогда не исполняется автоматически.

## 2. Принципы инженерного качества

1. **Никаких выдуманных прогнозов.** Прогноз включает только реализованные правила модели. Случайные будущие инциденты, не введённая погода и решения игрока не считаются известными.
2. **Одинаковая семантика исполнения и симуляции.** Каждый новый эффект действия обязан иметь парный регрессионный тест против живого действия.
3. **Ограниченная сложность.** У поиска есть жёсткие глубина, ширина и лимит команд; пользователь видит цель оптимизации и измеряемые последствия.
4. **Нет скрытой передачи данных.** В релизе 2.8.0 поиск выполняется локально. Сохранения и результаты не отправляются автоматически на сервер.
5. **Безопасное использование моделей.** Ключи OpenAI никогда не кладутся в HTML, JavaScript, Git или публичный конфиг. Подключение реальной модели допустимо только через защищённый серверный шлюз с лимитами расходов, строгой схемой вывода и журналом ошибок без персональных данных.
6. **Постепенная деградация.** Если браузер не поддерживает видеоэкспорт или тяжёлую функцию, базовый игровой цикл остаётся работоспособным.
7. **Проверяемая публикация.** Commit, прохождение тестов и открытая production-страница — три разных сигнала; ни один нельзя подменять другим.

## 3. Версия 2.9.0 — локальный автономный штаб со стресс-проверкой

### Входит в релиз
- Поиск допустимых очередей длиной 1–4 приказа с оценкой каскадов на T+30/T+60/T+90.
- Четыре функции цели с разными весами: **balanced**, **risk**, **protect**, **conserve**.
- Проверка доступного бюджета и числа бригад при оценке каждой последовательности.
- До трёх ранжированных вариантов с показателями риска, слабейшего узла, затрат и критических узлов.
- Явное применение: выбрать кандидат → загрузить в очередь → проверить → самостоятельно нажать исполнение.
- Инвалидация результата, когда изменилось состояние симуляции.
- Детерминированные регрессионные тесты для границ поиска, бюджетов, бригад, неизменности исходного состояния и повторяемости результата.

### Критерии приёмки
- Все метрики прогноза конечны и ограничены допустимыми диапазонами.
- Каждый предложенный план допустим по текущим ресурсам и бригадам.
- Поиск не меняет игровое состояние и выдаёт тот же результат при повторном запуске на том же состоянии.
- Планировщик не запускается в неустойчивом состоянии, требует паузы и не исполняет команды сам.
- Количество исследуемых комбинаций остаётся ограниченным верхним пределом; интерфейс остаётся пригодным для мобильного экрана.
- В манифесте релиза, UI-версиях и smoke-тесте совпадает номер сборки.

## 4. Следующие этапы

### Этап A — конвейер качества
- Проверять синтаксис встроенного JavaScript, JSON манифеста, уникальность HTML ID и все readiness-маркеры.
- Запускать regression smoke на каждый pull request.
- Проверять production route matrix после публикации, фиксируя HTTP-статусы, версию релиза и время ответа.
- Считать публикацию подтверждённой только после проверки публичного маршрута и версии снаружи.

**Gate:** тесты и route matrix проходят; нет секретов в артефактах; релизная версия совпадает во всех контрактах.

### Этап B — достоверность модели
- Добавить тесты на каждый порог каскада и на границы устойчивости узлов.
- Сравнивать прямые прогнозы с фактически применёнными действиями в контролируемых сценариях.
- Для каждой метрики показывать источник изменения: действие, связь инфраструктуры или реализованное правило симуляции.
- Не добавлять случайность в прогноз без воспроизводимого seed и отдельного описания неопределённости.

**Gate:** детерминированные тесты повторяются локально и в CI; необъяснённые расхождения запрещают релиз.

### Этап C — replay и сценарная лаборатория
- Сформировать воспроизводимые сценарии с seed и версией модели.
- Сохранять компактный локальный журнал действий и контрольные снимки, с экспортом только по явному действию пользователя.
- Добавить сравнение двух стратегий на одинаковом стартовом состоянии.
- Отдельно измерять обучение игрока: понимает ли он причины системных отказов, а не только набирает баллы.

**Gate:** воспроизводимость сценария подтверждена тестом; экспорт очищен от случайных и идентифицирующих данных.

### Этап D — опциональный OpenAI Advisor
- Оставить детерминированный движок источником истины для бюджета, симуляции и последствий.
- Поднять серверный endpoint с аутентификацией/ограничением частоты и бюджетом на пользователя или сессию.
- Хранить API-ключи только в серверных secrets; запретить передачу ключей на клиент.
- Передавать модели минимальный структурированный снимок состояния без личных данных.
- Требовать JSON по строгой схеме: гипотеза, причины, возможные действия, неизвестные факторы и предупреждения.
- Проверять все предложенные действия детерминированным симулятором до отображения пользователю. Модель не может самостоятельно исполнять команды.
- Иметь выключатель функции, лимиты токенов и стоимости, тайм-аут, отказобезопасный локальный режим и тесты prompt injection.

**Gate:** модель улучшает решения в слепом сравнении с локальным поиском; стоимость и задержка измерены; секреты и пользовательские данные защищены. Пока gate не пройден, нельзя маркировать игру как использующую OpenAI API.

### Этап E — производительность и выпуск
- Проверить настольный Chrome/Edge, мобильный Safari и Android Chromium на реальных устройствах.
- Измерить время поиска на типовых и стрессовых состояниях; задать бюджет времени для слабого телефона.
- При превышении бюджета уменьшить ширину поиска или выполнять его по частям, не замораживая интерфейс.
- Проверить клавиатурный фокус, экранные дикторы, уменьшение анимации, касания и длинные тексты на узком экране.
- Развёртывать сначала по опубликованному manifest, затем подтверждать версию внешней проверкой.

**Gate:** нет блокирующих ошибок, превышения согласованного времени отклика и расхождений между заявленной и фактической версией.

## 5. Система метрик

Измерять локально в тестах: время расчёта, количество рассмотренных допустимых планов, долю состояний без улучшения, улучшение риска на T+90, сохранность слабейшего узла, расход ресурсов, долю планов, отвергнутых валидатором, ошибки и отклонения реального результата от прогноза.

В продуктовой аналитике считать только добровольно предоставленные, агрегированные события. Не собирать содержимое сохранений, личные сведения или состояние города без явного согласия. Не называть открытие страницы, ссылку челленджа или показ варианта подтверждением реального пользователя, публикации либо конверсии.

## 6. Релизная дисциплина

Для каждого выпуска обязательны: изменённый контракт релиза, smoke-тест, проверка совместимости сохранений, краткие release notes, фиксация commit SHA и внешняя проверка production-версии. Если CI не запускался, пишется «CI не подтверждён». Если публичный маршрут недоступен проверочному инструменту, пишется «production не подтверждён». Никаких фиктивных процентов покрытия, бенчмарков или заявлений о 8K-рендеринге, если фактически использовано масштабирование.

## 8. Версия 2.9.0 — стресс-проверка штабной стратегии

Перед выдачей финальных рекомендаций система дополнительно прогоняет до восьми сильных кандидатов через три детерминированных отклонения от исходного состояния: усиление подтопления, перегрузка энергосети и повреждение слабейшего узла при сокращении резервов. Для каждого плана и каждого стресс-профиля без вмешательства используется одинаковый набор входных возмущений. Сравниваются риск T+90, целостность слабейшего узла и количество критических узлов.

Стресс-проверка меняет только копии прогнозируемого состояния, никогда не трогает живую симуляцию, не добавляет случайности и не выдаёт эти искусственные возмущения за прогноз погоды или реальные внешние данные. Рекомендации заново ранжируются по скорректированной оценке устойчивости; пользователь видит отдельный результат каждого из трёх тестов.

**Критерии приёмки:** ровно три ожидаемых стресс-профиля; не более восьми кандидатов проходят углублённую проверку; все метрики конечны; один и тот же стартовый снимок даёт одинаковый рейтинг; исходное состояние не меняется; новые поля контракта проверяются production route matrix; план не выполняется автоматически.



## 9. Версия 3.0.0 — парето-портфель и объяснимое решение

Одного числового рейтинга недостаточно для штабного решения: дешёвый план может быть хрупким, а устойчивый — потреблять слишком много резервов. Версия 3.0.0 сохраняет локальный beam search и стресс-проверку 2.9.0, затем выбирает до трёх вариантов из ограниченного парето-фронта.

Кандидат оценивается по пяти явным осям: скорректированная оценка плана (меньше лучше), затраты ресурсов (меньше лучше), худшее изменение риска в стресс-тестах (меньше лучше), худшее изменение целостности слабейшего узла (больше лучше) и число стресс-профилей, которые он выдержал без существенной деградации (больше лучше). Вариант исключается как доминируемый только тогда, когда другой не хуже по всем пяти осям и строго лучше хотя бы по одной.

Система по возможности показывает варианты с разными первыми двумя приказами, чтобы не выдавать почти одинаковые планы за значимые альтернативы. Для каждого варианта UI объясняет обычный прогноз относительно базы, количество устойчивых стресс-профилей, экономию ресурсов внутри показанного набора и самый неблагоприятный стресс-профиль. Эти объяснения — описание вычисленных показателей, а не сгенерированные заявления о контрфактической реальности.

**Критерии приёмки:** доминируемый вариант не попадает в парето-фронт; реальный компромисс цены и устойчивости не удаляется; возвращается не больше трёх вариантов; разнообразие стартовых префиксов максимально относительно реально исследованных кандидатов; результаты детерминированы; HTML, release manifest, smoke-тест и production-route matrix подтверждают одну версию; исходное состояние симуляции не меняется.



## 10. Версия 3.1.0 — воспроизводимое досье решения

Каждый экспортируемый разбор стратегии становится структурированным артефактом «osgard.civic-cascade.decision-dossier/v1». Он содержит версию игры и модели, имя и идентификатор сценария, используемые метрики и целостность узлов на момент расчёта, горизонты прогноза, базовую траекторию без новых приказов, возвращённый Pareto-портфель, последовательности приказов, затраты, оценки, все стресс-профили, ограничения поиска и явные допущения модели.

**Проверка происхождения:** SHA-256 вычисляется над канонической JSON-строкой полезной нагрузки, без поля exportMetadata, чтобы timestamp и контрольная сумма не создавали циклическую зависимость. Если Web Crypto недоступен, файл всё равно сохраняется, но отсутствие хеша явно отмечается. Хеш помогает обнаружить случайное изменение файла; он не является цифровой подписью и сам по себе не удостоверяет личность автора.

**Приватность:** отчёт формируется только по явному нажатию пользователя, скачивается браузером и не отправляется на сервер. В него не входят личные данные, аналитические идентификаторы или API-ключи. При изменении состояния игры после вычисления портфеля экспорт запрещается до нового расчёта.

**Критерии приёмки:** единый schema/version contract в HTML, release manifest, тесте и route matrix; валидный детерминированный payload; сохранение базового прогноза и каждого stress result; проверка отсутствия секретов и идентифицирующих полей; SHA-256 либо честно указанная недоступность Web Crypto; экспорт не меняет состояние симуляции.


## 11. Версия 3.2.0 — девятиточечный стресс-конверт

Версия 3.2.0 заменяет один уровень каждого синтетического возмущения на детерминированный диапазон чувствительности: **3 семейства × 3 уровня тяжести = 9 стресс-экспериментов**. Каждая альтернатива и базовая стратегия без новых приказов проходят один и тот же набор возмущений на горизонтах T+30/T+60/T+90.

### Матрица экспериментов
- **Подтопление:** мягкий, средний и тяжёлый уровень. Усиление пропорционально увеличивает добавку к воде и скорости роста водного давления.
- **Энергосеть:** мягкий, средний и тяжёлый уровень. Снижение доступности сети и рост скорости её ухудшения увеличиваются монотонно.
- **Удар по слабейшему узлу:** мягкий, средний и тяжёлый уровень. Целостность узла и снабжение уменьшаются пропорционально уровню.

Коэффициенты уровней заданы как 0,5 / 1,0 / 1,5 относительно среднего профиля. Это **синтетические нагрузки**, а не вероятностная модель реальной погоды или утверждение о физически откалиброванном городе. Для каждого профиля фиксируются семейство, тяжесть, коэффициент, состояние слабейшего узла, риск и изменение критических узлов относительно baseline под тем же возмущением.

### Пределы и критерии приёмки
- Ровно девять профилей; три семейства и по три монотонных уровня в каждом.
- Не более восьми кандидатов входят в дорогую стресс-проверку; портфель возвращает не более трёх стратегий.
- Все девять профилей включены в JSON-досье со значениями до/после и сравнимым baseline.
- Ранжирование воспроизводимо и не меняет рабочее состояние; возмущение применяется только к копии состояния.
- HTML, manifest, regression smoke и production route matrix согласованы по релизу 3.2.0 и перечню девяти профилей.
- Вывод остаётся локальным: без телеметрии, пользовательских данных и запросов к OpenAI API.

### Почему это сильнее ещё одного балла
План больше нельзя назвать устойчивым на основании одного произвольно выбранного уровня нагрузки. Отчёт показывает диапазон реакции модели и худший уровень в каждом семействе, позволяя заметить стратегию, которая работает при среднем стрессе, но ломается при тяжёлом. Это повышает проверяемость решения, но не доказывает реальную причинность за пределами реализованной модели.



## 11. Версия 3.3.0 — проверяемое досье решений

### Семь инженерных усилений
1. **Канонический JSON.** SHA-256 вычисляется для рекурсивно упорядоченного JSON: порядок ключей объектов не меняет хеш, порядок элементов массивов сохраняется. Хеш формируется до добавления экспортных метаданных.
2. **Локальный импорт-верификатор.** Пользователь может открыть ранее экспортированный JSON в интерфейсе и проверить отчёт без загрузки на сервер.
3. **Обнаружение изменений.** Любое изменение содержимого, влияющее на канонический payload, приводит к несовпадению SHA-256; отчёт помечается как изменённый или повреждённый.
4. **Строгая валидация схемы.** Проверяются ID движка, модель, сценарий, исходный снимок, прогнозы 30/60/90, стоимость и бригады, типы команд, цели ремонта и полный набор девяти стресс-профилей.
5. **Защита от перегруженных файлов.** Максимум 1 МиБ, глубина 32 уровня, 50 000 JSON-элементов, не более трёх кандидатов и четырёх приказов. Неизвестные команды и значения за пределами диапазонов отвергаются.
6. **Совместимость моделей.** Валидное историческое досье можно изучать, но оно помечается как отчёт другой версии и не объявляется напрямую сравнимым с текущей моделью. Поддержан legacy-хеш версий до каноникализации.
7. **Безопасное представление и регрессии.** Все строки импортированного файла выводятся через textContent; ни один импортированный приказ не исполняется. Тесты покрывают изменение хеша, перестановку ключей, плохую схему, недопустимые команды, нарушения приватности, неполный стресс-набор и чрезмерную глубину JSON.

### Предел доказательства

SHA-256 здесь проверяет совпадение файла с хешем внутри этого же файла. Это выявляет случайное или последующее изменение, но **не является цифровой подписью**: авторство требует внешнего доверенного ключа или сервиса подписи. Проверка полностью локальна, не вызывает OpenAI API и не отправляет телеметрию.

**Gate релиза:** фронтенд smoke проходит; тест досье подтверждает детерминированность canonical JSON и tamper detection; route matrix требует новую версию и все новые маркеры; импортированные команды никогда не применяются к игровому состоянию.
