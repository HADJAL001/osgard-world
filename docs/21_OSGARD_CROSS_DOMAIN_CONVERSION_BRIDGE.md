# OSGARD — серверная атрибуция конверсий экосистемы

**Статус:** интерфейс приёма событий и схема базы добавлены в ветке `feat/server-side-service-conversions`; домены назначения ещё не подключены автоматически.

## Зачем

Игровой портал уже умеет измерять видимые показы собственных карточек OSGARD SELECT, клики, игровые сессии и приглашения при согласии пользователя. Но переход на другой домен не доказывает, что там зарегистрировались, забронировали услугу или оплатили заказ. Для коммерческого анализа нужен обратный сигнал от сервера целевого проекта.

## Поток

1. Игра или каталог показывают собственную карточку с метками источника и кампании.
2. Целевой проект сохраняет допустимые UTM-поля вместе со своим внутренним объектом регистрации/заказа, получив при необходимости согласие на атрибуцию.
3. Его сервер подтверждает событие в собственном источнике истины: база продукта, booking-система или платёжный провайдер.
4. Целевой сервер отправляет минимальный payload на `POST /v1/attribution/conversions` с индивидуальным bearer-токеном.
5. Commerce API проверяет формат и токен, пишет событие в `commerce_attribution_conversions` с составным ключом `(service_id, event_id)`, возвращает безопасный результат при повторном событии.
6. Закрытая панель OSGARD показывает конверсии и заявленные суммы по сервису, игре-источнику, кампании и валюте.

## Безопасность и данные

- Секреты каждого сервиса хранятся только в серверных переменных; ни один секрет не передаётся браузеру.
- Payload не имеет полей для имени, телефона, email, свободного текста и customer ID.
- `eventId` — уникальный непрозрачный идентификатор события в целевой системе; повтор отправки не повышает метрики.
- Для событий покупки/возврата сумма должна быть положительной целочисленной величиной в младших единицах указанной валюты. Отчёт применяет возврат как отрицательное движение.
- Для неплатёжных событий сумма и валюта запрещены.
- `consent: true` должен опираться на реально записанное согласие в целевом сервисе, если оно требуется для данного сценария. Не посылай события только потому, что на URL есть UTM.
- Серверный bearer token доказывает, какой интегратор прислал запись; он не является независимым доказательством оплаты. Для платежей событие отправляется после серверной проверки у источника истины.
- Суммы группируются по валютам. Нет одной суммарной «долларовой выручки», пока валюты не пересчитаны по документированному курсу и дате.
- Хранение conversion records в этой версии ограничено 365 днями; логи должны не включать тело запроса или секреты.

## Схема события

Поддерживаемые типы:

- `account_created`, `lead_qualified`, `trial_started`, `booking_confirmed`;
- `purchase_paid`, `purchase_refunded`;
- `subscription_started`, `subscription_renewed`, `subscription_refunded`, `subscription_cancelled`.

Пример без платёжных полей:

```json
{
  "consent": true,
  "serviceId": "senjorio",
  "eventId": "booking-record-opaque-12345",
  "conversionType": "booking_confirmed",
  "gameId": "civic-cascade",
  "source": "osgard_games",
  "campaign": "after_game"
}
```

Пример после серверно подтверждённого платежа:

```json
{
  "consent": true,
  "serviceId": "marcosa",
  "eventId": "payment-provider-event-12345",
  "conversionType": "purchase_paid",
  "gameId": "signal-run",
  "source": "osgard_games",
  "campaign": "after_game",
  "referralCode": "og_a1b2c3d4",
  "amountMinor": 2599,
  "currency": "SEK"
}
```

## Очерёдность подключения проектов

Начать с одного проекта, у которого точно есть серверная система учёта и подтверждаемое целевое событие. После сквозного теста добавить остальные серверы индивидуальными секретами. Предварительная очередь для ручного подтверждения владельцем продукта:

1. **OSGARD BEW WORLD** — подтверждённая заявка/создание проекта, затем покупка только при наличии платежа.
2. **O2 SYSTEM** — оплаченный заказ или квалифицированный коммерческий запрос, если эти события уже доступны серверу.
3. **SENJORIO** — подтверждённое бронирование; не путать клик с заказом.
4. **SUPERDAY.RUN** — регистрация/активация планировщика, если такой серверный аккаунт существует.
5. **MARCOSA.CLUB** и **MYOSA.WORLD** — подтверждённая регистрация, подписка или покупка после проверки серверной модели.
6. **GOLD GLAMOUR**, **OSGARD OS**, **OSGARD VANGUARD STUDIO**, **GARD VPN** — только после обнаружения подходящего серверного события. Если конкретный проект работает как статический сайт, он пока может измерять только клик или заявку, а не внутреннюю конверсию.

Этот порядок — план реализации, а не утверждение, что перечисленные интеграции уже существуют.

## Критерии завершения интеграции

- уникальный секрет создан и хранится только на сервере назначения и Commerce API;
- source/campaign/referral code валидируются и сохраняются у сервиса назначения после допустимого согласия;
- тестовый signup/booking/payment вызывает API, а повтор того же `eventId` не дублирует сумму;
- возврат формирует отдельное событие с исходной валютой и суммой;
- панель администрирования показывает тестовые строки с правильной валютой;
- ключи, персональные контакты и идентификаторы аккаунтов отсутствуют в URL, клиентском коде и логах;
- в отчётах остаётся заметное различие между промо-показом, кликом, conversion event и фактически полученной выручкой.
