# CASCADE LAB 0.26.0 — Reproducibility Kernel

## Что выпущено в этой версии

Reproducibility Kernel превращает результат запуска в переносимый технический паспорт. Он связывает четыре вещи: условия физической модели, схему устройств, реально записанную траекторию и измерения конечного результата.

Каждый завершённый запуск публикует локальное событие `cascade-lab:run-finished` с версионированным контрактом `osgard.cascade-lab.physics-contract.v1`. Контракт содержит идентификатор ревизии физики, фиксированный шаг интегрирования, параметры мира, численные настройки движка и геометрию уровня. Новая лаборатория записывает до 420 кадров траектории, порядок установленных устройств, основные измерения и три отпечатка.

### Что означает сравнение

- **Exact repeat** — совпали отпечаток физического контракта, конфигурация устройств, трасса, исход и включённые в паспорт измерения.
- **Near repeat** — условия и схема одинаковы, среднее отклонение выбранных точек траектории мало, но журнал результата не совпал полностью.
- **Trace drift** — условия и схема одинаковы, однако траектория, измерения или исход отличаются.
- **Different contract / blueprint / scenario** — это не корректная пара для теста повторяемости. Система объясняет, какое условие не совпадает, вместо того чтобы делать причинный вывод.

Архив хранит не более 12 паспортов в локальном хранилище браузера. Поддерживаются экспорт отдельного паспорта, экспорт архива и проверяемый импорт JSON. Импорт ограничен размером 900 KiB, числом записей, схемой данных и уникальностью ID.

## Ограничения, встроенные в проект

Отпечатки создаются FNV-1a-32 над канонизированными данными. Это небольшой детерминированный контроль целостности для обнаружения распространённых случайных правок, **не криптографический хэш, не цифровая подпись и не доказательство авторства**. Возможны коллизии и намеренная подделка.

Паспорт также не доказывает, что симуляция физически верна. Он фиксирует, какую модель игра заявила и какие результаты эта модель записала. Сверка между разными браузерами и устройствами пока не равнозначна побитовой детерминированности движка. Реальные параметры игры, контрольные тесты и версия контракта должны эволюционировать вместе.

Все данные Reproducibility Kernel остаются на устройстве до отдельного действия экспорта или импорта. Модуль не передаёт запуски по сети и не использует данные игроков для обучения. Это локальный инженерный журнал, а не онлайн-рейтинг и не научно валидированный физический симулятор.

## Три года инженерного развития

Горизонт ниже — план, а не заявление о уже выполненной работе. Каждая фаза начинается с измеримого контракта, набора эталонных сценариев и регрессионных тестов.

### Год 1 — воспроизводимый движок

**Цель:** превратить одиночный браузерный симулятор в измеряемую систему с контролируемыми изменениями.

1. Зафиксировать полный Physics Contract: каждый численный параметр, порог, порядок вычислений, правила контактов, таймеры и условия победы.
2. Создать golden corpus — версионированные эталонные сценарии для пружины, конвейера, воздушного потока, магнита, отбойника, контакта, шлюза, сканера, хрупкого груза и тайм-аута.
3. Для каждого сценария сохранять начальное состояние, порядок шагов, контрольные кадры, события и допустимые погрешности.
4. Разделить функциональные тесты, тесты математических инвариантов, тесты импорта и браузерные сценарии; мутации движка должны выявляться отдельными тестами.
5. Добавить автоматическое сравнение предыдущей версии физики с новой и отчёт о том, какие эталонные сценарии изменились.
6. Сохранять понятный экспорт паспорта с версией движка, схемой, настройками мира и указанием ограничений проверки.

**Предлагаемые цели для проверки в конце фазы:**
- 100% критичных правил победы/поражения покрыты контрактными сценариями;
- каждый релиз физики проходит полный набор эталонных запусков;
- ни одно отличие результатов не считается регрессией или улучшением без описанного допуска и воспроизводимого примера;
- всякий импорт получает однозначный результат проверки: принят, отклонён или несовместим.

### Год 2 — сравнение устройств и независимые повторения

**Цель:** отличать эффект реального изменения схемы от различий окружения исполнения.

1. Запустить матрицу воспроизводимости по поддерживаемым браузерам, размерам экрана и классам устройств.
2. Зафиксировать, что сравнивается в каждой среде: сборка, версия движка, частота обновления, время сценария, шаг интеграции, настройки уровня и данные ввода.
3. Проверять одну переменную за эксперимент; дополнительные изменения автоматически помечать как конфаундеры, а не как чистый A/B-тест.
4. Создать набор сцен с повторениями N раз, чтобы оценивать распределение времени, траектории и ударных скоростей, а не только один результат.
5. Разработать явную систему версий архивов и миграций с безопасным отказом при несовместимости.
6. Рассматривать обмен паспортами между игроками только как явное пользовательское действие; перед любой онлайн-функцией отдельно спроектировать согласие, минимизацию данных и сроки хранения.

**Предлагаемые цели для проверки в конце фазы:**
- межбраузерный тест отделяет точное совпадение от допуска по траектории;
- все сравнения показывают размер выборки и правила допуска;
- импорт неизвестной версии не приводит к потере текущих записей;
- сетевые функции, если они будут одобрены отдельно, выключены по умолчанию и не получают сырую телеметрию без явного согласия.

### Год 3 — доказуемые инженерные рабочие процессы

**Цель:** сделать воспроизводимость частью полного цикла изменения игры, а не отдельной панелью.

1. Ввести physics CI: каждый pull request с изменением движка запускает эталонные сценарии и прикладывает отчёт о различиях.
2. Добавить дифференциальные тесты для независимых реализаций физических правил и, если это оправдано, сравнить браузерный движок с отдельным reference solver.
3. Разделить статус результата на: структура проверена, отпечаток совпал, траектория совпала в пределах допуска, физическое свойство подтверждено эталонным тестом. Не сводить их к единому зелёному значку.
4. Построить объяснимый coaching-слой, который ссылается на реальные события, может ответить «данных недостаточно» и предлагает только следующий контролируемый тест.
5. Рассмотреть перенос физической модели в Godot только после определения общего контрактного набора и проверки расхождений двух реализаций.
6. Криптографически подписанные паспорта или удалённые аттестации разрабатывать только при реальном требовании доверия: с моделированием угроз, управлением ключами и независимым аудитом, не заменяя это простым хэшированием.

**Предлагаемые цели для проверки в конце фазы:**
- каждая сборка имеет воспроизводимый отчёт о результатах эталонных сценариев;
- каждый вывод coaching привязан к наблюдению и уровню уверенности;
- неподтверждённые утверждения явно помечаются, а система умеет воздерживаться от диагноза;
- перенос движка принимается только после прохождения общего набора проверок, а не по совпадению интерфейса.

## Release gates

Перед публикацией нужно проверить:

1. Единственную каноническую версию страницы и правильную загрузку всех слоёв 0.17–0.26.
2. Unit-smoke для паспорта: одинаковая трасса, дрейф, иной контракт, иной порядок устройств, повреждённые поля, дублированные ID и завышенный архив.
3. Регрессии всех предыдущих слоёв — Delta Lens, Hypothesis Lab, Engineering OS, Experiment Studio, Case Passport, Trajectory X-Ray, Mission Director и Evidence Integrity.
4. Production route matrix для страницы, контракта, модуля и служебного worker; отдельно убедиться в desktop/mobile доступности.
5. Успешное прямое развёртывание с проверкой архива, контрольной суммы, активации и HTTP-ответов. Наличие commit или pull request само по себе не является подтверждением публикации.

Команда нового независимого теста: `npm run qa:cascade-lab-reproducibility`. Она включена и в общий `qa:games-detail`.

## Решение по архитектуре

Не строить «магический AI, который угадывает физику». Строить систему, где каждый следующий уровень интеллекта имеет проверяемый источник данных: сначала контракт, потом эталонные тесты, потом сравнение, затем рекомендации. Генеративная модель может объяснять результат и предлагать эксперимент, но физический движок и проверочные тесты остаются источником измерений. Это позволит добавлять AI-инструменты без смешивания наблюдений, гипотез и доказательств.
